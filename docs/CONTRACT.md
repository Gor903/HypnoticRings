Приоритет источников: `design/GAME_DESIGN_SPEC.md` → (GDD отсутствует, см.

## 1. Жанр и основной цикл

**Жанр:** бесконечная одножестовая аркада на 2D-физике, портрет, оффлайн.

**Цикл** (переписан в D-058). Шарик **летает** внутри кольца `E`, отскакивая
от его стенки без потери энергии. Игрок водит пальцем по кругу — все кольца
поворачиваются на один и тот же угол. Когда отверстие оказывается на пути
шарика, тот вылетает наружу, получает +1 очко, а покинутое кольцо
растворяется. Одновременно все кольца стягиваются к центру `O`: не успеешь —
кольцо дойдёт до красного круга в центре.

**Условие поражения** (ровно два, оба геометрические, не по коллизиям):

1. **Красный круг.** Внутренняя кромка ближайшего к центру живого кольца
   достигла красного круга: `R − T/2 ≤ redRadius` (`redRadius = 0.75`, D-059). Круг
   рисуется ровно этим радиусом, поэтому граница видна, а не угадывается.
   Положение шарика в условии **не участвует**.
2. **Вылет.** Расстояние от центра шарика до `O` превысило `R_E + 2s` — защита
   от багов, в нормальной игре не срабатывает.

**Условия победы нет** — игра бесконечна. Метрика результата — счёт.

**Направления, чтобы не перепутать.** Кольцо `E` — то, внутри которого сейчас
шарик; оно снаружи от него. Прохождение кольца двигает шарик **наружу**, сжатие
тоннеля тянет кольца **внутрь**. С D-058 «низ» больше не особое место: шарик
летает и выходит в любое отверстие, до которого долетит.

## 2. Сущности и правила — слой чистой логики

Всё в этом разделе формулируется без типов движка и становится сборкой
`HR.Core` (см. §6). Числа — стартовые значения `GameConfig`, не константы в
коде.

### 2.1. Единицы

| | |
|---|---|
| Мировая единица `u` | единица движка. Шарик `D = 0.54u`, `r = 0.27u` (D-059) |
| Углы | `0°` вправо, `90°` вверх, `270°` вниз; против часовой — плюс |
| Центр тоннеля | `O = (0,0)` |
| Гравитация | `(0, −g)`, `g = 14 u/s²` |

### 2.2. Кольцо

Состояние: `id`, радиус центральной линии `R`, угол центра отверстия
`gapAngle` (°), длина дуги отверстия `w` (u), автономная угловая скорость
`ω_auto` (°/с), число отверстий (1, поздно 1–2), `colorIndex`.

Правила:

- Толщина `T = 0.40u`, одинакова у всех колец, во всех темах, всегда. Физическая
  толщина равна визуальной.
- **Держится угол, а не длина дуги** (D-059): `θ = (w + T) / R_target` и дальше
  не меняется, сколько бы кольцо ни сжималось. `w` — чистый просвет на
  равновесном радиусе; снаружи от него отверстие шире в `u`, внутри — уже, но
  угол тот же, и кольцо не разваливается по мере приближения к центру.
- Единственное исключение — пол проходимости, и он физический: при `R < R_target`
  угол не опускается ниже `(w_min + T) / R`, то есть растёт ровно настолько,
  чтобы шарик всё ещё проходил, и не быстрее.
- `w_min = 0.80u` — это пол **проходимости**, а не вкуса: чистый просвет, в
  который шарик диаметром 0.54u ещё проходит. Самая узкая строка кривой (1.29u)
  выше него с запасом, так что для кривой он работает только как страховка.
- Физические концы отверстия всегда скруглены радиусом `T/2`; шарик не
  застревает на острых углах. Визуальная форма концов — дело темы.
- Коллайдеры: тело кольца режется на сегменты ≤ 120°, шаг аппроксимации дуги
  ≤ 7.5°. Отверстие — пустота, коллайдеров в нём нет.
- **Стеной является только кольцо шарика и два снаружи от него** (D-059).
  Остальные нарисованы, но выключены из физики: шарик заперт внутри своего
  кольца и до следующих дотянуться не может, а с десятью кольцами в кадре
  Box2D проверял его против тридцати полигонов, которых он не касается.
- Угол поворота кольца = `userAngle + накопленное ω_auto·t`. Пользовательская
  компонента одна на все кольца, автономная — своя у каждого.

### 2.3. Шарик

| | |
|---|---|
| Диаметр / масса | 0.54u / 1 (D-059) |
| Трение / упругость шарика | 0.0 / 1.0 (D-058) |
| Трение / упругость кольца | 0.0 / 1.0 (D-058) |
| Крейсерская скорость | 10 u/s, подтяжка 5 u/s² каждый шаг (D-059) |
| Доля гравитации | `gravityScale = 0.15` — гнёт траекторию, не разгоняет |
| Порог отскока | `Physics2D.bounceThreshold = 0.01` (D-058) |
| Максимальная скорость | 16 u/s, ограничивается каждый физический шаг |
| Детекция столкновений | Continuous + Interpolate |
| Фиксированный шаг | 1/90 с |

Шарик не телепортируется и не двигается заданной анимацией — только физикой.
С D-058 он **летает**: упругие отскоки без трения, а регулятор возвращает
модуль скорости к крейсерской, компенсируя и потери, и энергию, которую даёт
движущаяся стенка. Направление регулятор не трогает — оно принадлежит тому, обо
что шарик только что ударился.

### 2.4. Геометрия тоннеля

| Параметр | Значение |
|---|---|
| Просвет коридора `c` | 0.95u — 1.76 диаметра шарика (D-059) |
| Шаг колец `s = c + T` | 1.35u |
| Равновесный радиус `R_target` | 3.0u |
| Радиус исчезновения `R_vanish` | 1.05u |
| Колец снаружи от шарика `K_ahead` | 9 (D-059) |
| Полукадр камеры `orthoSize` | 10.0u, центр тоннеля на 72% высоты |

**Начальная расстановка** (спецификация задаёт её словами; числа закреплены
здесь): шарик **запускается** внутри кольца `E` с `R = R_target = 3.0` —
случайная точка на радиусе 2.40–2.53 и случайное направление, скорость
`cruiseSpeed`; снаружи девять колец при `4.35`, `5.70`, `7.05`, `8.40`, `9.75`,
`11.10`, `12.45`, `13.80`, `15.15` — ровно столько, чтобы тоннель доходил до
нижнего края кадра, а не обрывался на фоне. Кольца **внутри** шарика нет: кольцо, из которого шарик вышел,
растворяется за 0.25 с и уходит в пул (D-058).

### 2.5. Сжатие

```
v_eff = clamp( v_base + k_pull · (R_E − R_target),  v_base,  v_max )
R_i ← R_i − v_eff · dt          для всех колец одновременно
```

`k_pull = 3.0 1/с`; `v_base` и `v_max` — оба от сложности (§2.7), это две
независимые ручки с D-058.

Все кольца сжимаются с одной скоростью, поэтому `c` и `s` постоянны и физика
коридоров не меняется со временем. После прохода `R_E` скачком вырастает на
`s`, и `v_eff` упирается в `v_max` — это и есть «втягивание тоннеля»,
отдельного эффекта для него не делается. На старте `v_max = 1.0`, поэтому
втягивание мягкое; прежняя жёсткая 4.0 работала с первого же кольца.

Кольцо без шарика внутри при `R < R_vanish` гаснет и возвращается в пул.
Кольцо, внутри которого шарик, не удаляется никогда — оно может сжаться до
раздавливания. Новое кольцо рождается снаружи, когда колец снаружи от кольца
шарика стало меньше `K_ahead`.

### 2.6. Прохождение кольца

`OnRingPassed(ringId)` вызывается **ровно один раз** на кольцо, когда
выполнены оба условия:

1. расстояние от центра шарика до `O` больше `R_E + T/2 + 0.22`;
2. шарик находится в коридоре кольца `E+1`.

### 2.7. Сложность

Функция числа пройденных колец `n`, интерполируется плавно; скачок между
соседними кольцами не более 15%.

Опоры живут в ассете `Config/DifficultyTable.asset`, а не в C# (D-058).

| Параметр | n=0–2 | n=10 | n=30 | n=80+ |
|---|---|---|---|---|
| `v_base` (u/s) | 0.45 | 0.55 | 0.70 | 0.85 |
| `v_max` (u/s) | 2.0 | 3.0 | 4.0 | 5.0 |
| `w` (u) — просвет на `R_target` | 4.10 | 3.70 | 3.27 | 2.60 |
| Угол отверстия (°) | 86 | 78 | 70 | 57 |
| `|ω_auto|` (°/с) | 0 | 15 | 40 | 70 |
| Бюджет до красного (с) | 4.56 | 3.73 | 2.93 | 2.41 |
| Кольцо раз в (с) | 3.00 | 2.45 | 1.93 | 1.59 |
| Направления соседей | одинаково | чередуются | случайные | случайные |
| Отверстий | 1 | 1 | 1 | 1 |

**Отверстия заданы углом, а не долей от шарика, и это следствие D-058.** Пока
шарик лежал на дне, ширина решала, насколько точно надо прицелиться. Летающий
шарик выходит в то отверстие, до которого долетел, поэтому шанс выйти за
секунду пропорционален **углу** отверстия — и при удержании угла (D-059) его
пришлось поднять до 86°–57°. Это ровно те углы, которые старая игра показывала
у рабочего радиуса (67°–36°) и дальше раздувала вдвое-втрое; теперь они
постоянны. Проверено гейтом на реальной физике: средний бот 291/300.

`v_base` — таймер до красного круга, `v_max` — потолок втягивания после
прохода. Это две разные ручки с D-058: раньше одна 4.0 на всю игру упиралась в
потолок уже на первом кольце. Второе отверстие не делается: массив на два
отверстия убран, `_gapCount` всегда 1 (D-058).

Первые три кольца — обучение: не вращаются сами, широкие отверстия, медленное
сжатие.

### 2.8. Гарантия проходимости (правило генератора)

Для каждого нового кольца генератор обязан обеспечить

```
|Δ| / (ω_comfort − |ω_auto|)  ≤  0.6 · T_budget
```

`Δ` — минимальное по модулю угловое расстояние (°) от предполагаемой позиции
шарика до отверстия; `ω_comfort = 300 °/с` (D-059: при чувствительности 3.0 это
всего 100 °/с пальцем); `T_budget = (R_target − T/2 − redRadius) / v_base =
2.05 / v_base`. Если `|ω_auto| ≥ ω_comfort`, то
`ω_auto` обрезается до `0.5·ω_comfort`. Пока условие не выполнено — генератор
двигает отверстие.

Скорости автономного вращения соседних колец различаются не менее чем на 20%
(кроме обучающих). Сид генерации сохраняется.

### 2.9. Счёт и прогресс

+1 за кольцо, без комбо и множителей. Рекорд сохраняется.

| Тема | Условие открытия |
|---|---|
| Monochrome, Midnight, Neon | сразу |
| Pastel | рекорд ≥ 25 |
| Earth | рекорд ≥ 50 |

### 2.10. Управление

`φ = atan2(touch − O_screen)`; `Δφ` за кадр с нормализацией через ±180°;
`userAngle += Δφ · sensitivity` — добавляется всем кольцам сразу.

| Параметр | Значение |
|---|---|
| `sensitivity` | 2.0 базовая, ползунок настроек умножает её на 0.6–1.6 (D-057) |
| `maxUserAngularSpeed` | 900 °/с (D-057) |
| `inertiaDecay` | 5.0 1/с, экспоненциальное затухание после отпускания |
| `deadZoneRadius` | 0.6u в экранной проекции |
| Мультитач | только первый палец |
| Инверсия | опция настроек |

Касание принимается в любом месте экрана, не только по кольцам.

### 2.11. Что не может жить в `HR.Core`

Честно, чтобы не делать вид, что ядро покрывает всё: **симуляция контакта
шарика с дугой — это `Rigidbody2D`, и переписывать её в чистый C# нельзя.**
Это прямое требование GDD и спецификации §4 («честная физика»).

В `HR.Core` уходит и покрывается EditMode-тестами:

- вся геометрия (`θ = w/R`, попадание угла в отверстие, расстояния, условие
  раздавливания, условие прохождения);
- закон сжатия `v_eff`;
- кривая сложности и генератор с проверкой проходимости (§2.8);
- состояния игры, счёт, разблокировка тем;
- форма сохранения, её версия и миграция;
- таблица строк и выбор языка;
- расчёт контраста тем.

В PlayMode-тестах проверяется то, что без движка не проверить: отсутствие
туннелирования, поведение шарика на вращающемся кольце, жесты через
`InputTestFixture`, бот-симуляции, утечки и рестарты.

## 3. Экраны и переходы

```
Boot ──► Menu ──► Playing ──► GameOver ──► Playing (Retry)
          │  ▲        │  ▲         │  │
          │  │        ▼  │         │  └──► Menu (Home)
          │  │     Paused│         └─────► ThemeSelect ──► GameOver
          │  ├──► Settings ──┘
          │  └──► ThemeSelect ──► Menu
          └──► (Back на Android) ──► выход из приложения
```

| Переход | Чем вызывается |
|---|---|
| Boot → Menu | загрузка сохранения завершена |
| Menu → Playing | кнопка Play; появление тоннеля 0.4 с |
| Playing → Paused | кнопка паузы, потеря фокуса, кнопка Back |
| Paused → Playing | Resume |
| Paused → Menu | Home |
| Playing → GameOver | раздавливание; анимация смыкания 0.8 с |
| GameOver → Playing | Retry (нижняя треть экрана) |
| GameOver → Menu | Home |

**Первый запуск** отличается ровно одним: в Playing показывается подсказка
«Проведи пальцем по кругу» с анимированным жестом, и она исчезает навсегда
после первого поворота колец. Флаг хранится в сохранении.

## 5. Чего исходные документы не говорят — решено здесь

Самый ценный раздел: каждая строка — то, что пришлось бы выяснять посреди
реализации.

| # | Пробел | Решение | Кто решил |
|---|---|---|---|
| G-01 | Переживает ли **незавершённый забег** смерть процесса | Нет. Сохраняются только рекорд, тема, открытые темы, настройки, флаг подсказки. После убийства процесса запуск ведёт в Menu. Забег длится секунды–минуты; восстановление физического состояния посреди падения шарика дороже и менее честно, чем перезапуск | агент |
| G-02 | Что происходит при **возврате из фона** | Playing → Paused автоматически, жест сброшен, инерция обнулена. При Resume — затухание 0.3 с, в течение которого физика стоит. Мгновенная смерть сразу после возврата невозможна | агент |
| G-03 | **Поворот экрана** | Не бывает: портрет зафиксирован (`DECISIONS.md`, часть A). Фаза 13 проверяет, что поворот устройства ничего не меняет | агент |
| G-04 | Что показывает **свежая установка** до первого забега | В меню строка рекорда скрыта, пока рекорд = 0; в HUD строка `Best` тоже скрыта. Пустое «Рекорд: 0» — шум | агент |
| G-05 | **Значения по умолчанию** звука, музыки, вибрации, эффектов | Звук вкл (1.0), музыка вкл (0.7), вибрация вкл, «Снизить эффекты» выкл, чувствительность 1.0, инверсия выкл, язык Авто | агент |

| G-08 | Нужен ли **отсчёт 3-2-1** при Resume | Нет. Вместо него физика заморожена на время затухания 0.3 с (см. G-02). Отсчёт — функциональность вне MVP | агент |
| G-09 | Разрешение **`VIBRATE`** в манифесте | Вибрация требуется спецификацией §11.4, значит `android.permission.VIBRATE` остаётся в манифесте и честно отражается в листинге. Удаляются `INTERNET`, `ACCESS_NETWORK_STATE`, `AD_ID`. Целевой список разрешений артефакта: **ровно `VIBRATE` и ничего больше** | агент |
| G-10 | **Камера:** план §2 требует следования за шариком и подбора масштаба, спецификация §11.1 — «орто, статична» | Статична (спецификация старше по приоритету). D-057 и D-059 | агент, по правилу приоритета документов |
| G-11 | **minSdk:** план §2 говорит 24, каталог разработчика — 26 | 26. Перечисление Unity 6000.6 начинается с 26, и с 26 adaptive icons нативны. Проверяется программно в фазе 10 | агент |

| G-14 | Поведение при **`deltaTime` = 0 или огромном** | Физика на фиксированном шаге; игровая логика ограничивает `dt` сверху значением 0.1 с. Проверяется тестом фазы 9 | агент |

Поля `soundVolume` и `musicVolume` в сохранении существовали с фазы 6, но управления у них не было — переключатель отличает «тише» от «выключено», и нужны оба | агент |
| G-16 | **Выбор темы:** §10.4 требует горизонтальную карусель карточек с превью, названием и условием открытия | Карусель сделана. ## 6. Архитектура

Сборки (`Assembly Definition`) и что кому разрешено ссылаться:

| Сборка | Ссылается на | Содержит |
|---|---|---|
| `HR.Core` | **ничего из UnityEngine** | геометрия, сжатие, сложность, генератор, состояния, счёт, форма сохранения, строки, контраст |
| `HR.Gameplay` | `HR.Core`, UnityEngine | `RingController`, `RingMeshBuilder`, `BallController`, `TunnelController`, `CameraRig`, пул |
| `HR.Input` | `HR.Core`, Input System | `InputController`, жест, инерция, мёртвая зона |
| `HR.Themes` | `HR.Core`, UnityEngine | `ThemeData`, `ThemeApplier`, `ThemeManager` |
| `HR.Audio` | `HR.Core`, UnityEngine | `AudioManager`, пул источников |
| `HR.Save` | `HR.Core`, UnityEngine | `SaveService`, атомарная запись, миграция |
| `HR.UI` | `HR.Core`, `HR.Themes`, `HR.Save`, uGUI | экраны, `SafeAreaFitter` |
| `HR.Editor` | всё выше | `SceneBuilder`, `ReleaseTool`, `ScreenshotTool`, генераторы |
| `HR.Tests.EditMode` | `HR.Core` и остальные | тесты без сцены |
| `HR.Tests.PlayMode` | всё | тесты со сценой, бот |

Граница, которая держит всю конструкцию: **`HR.Core` компилируется без
единой ссылки на движок.** Это проверяется гейтом фазы 0, а не намерением.

Разделение ответственности внутри геймплея — по таблице спецификации §3.5:
`RingController` не знает о цвете, `ThemeApplier` не трогает ни одного
физического параметра, `TunnelController` не знает о пальце.

## 7. Не делается в v1

Реклама, внутриигровые покупки, онлайн, аналитика, таблицы лидеров,
достижения, ежедневные задания, мультиплеер, облачные сохранения, управление
отдельными кольцами, 3D. Всё это — в `BACKLOG.md`, и ни одна строка кода на
это не тратится.

Отдельно: **никаких сетевых разрешений**, потому что это единственный способ
честно заполнить Data Safety.

## 8. Открытые вопросы к человеку

Блокирующих нет. Четыре вещи человек делает сам, и ни одна не мешает работать
до фазы 12:

1. Подтвердить пять необратимых решений (`DECISIONS.md`, часть A) — до первой
   загрузки, не до написания кода.
2. Вход в хостинг политики конфиденциальности (`wrangler login`) — токен не
   должен попасть агенту.
3. Прогон на реальном телефоне по чек-листу.
4. Всё, что происходит внутри Play Console.
