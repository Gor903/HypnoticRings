# Hypnotic Rings — автономный план для Claude Code (от А до релиз-готового состояния)

Этот файл — главный план работ. Исходные документы: `docs/GDD.md` (Game Design Document) и референсы `docs/reference/ref_minimal.png` (чёрные тонкие кольца с закруглёнными концами, белый фон, шарик по центру) и `docs/reference/ref_neon.png` (портретный экран, тёмно-синий фон, толстые цветные сегментированные кольца, счёт сверху по центру, внутренние кольца меньше и тоньше — эффект глубины тоннеля).

**Приоритет документов:** `docs/GAME_DESIGN_SPEC.md` (точная механика, формулы, числа, макеты экранов, палитры тем) → `docs/GDD.md` (идея) → этот план (порядок работ). Раздел «Механика по умолчанию» ниже — краткая выжимка; подробности и числа всегда берутся из `GAME_DESIGN_SPEC.md`.

Цель: Claude Code самостоятельно, без участия человека, доводит проект до состояния «готов к загрузке в Google Play»: подписанный `.aab`, проходящие тесты, сторовые материалы, документация.

## 0. Правила работы (контракт автономности)

1. **Не задавать вопросов человеку.** Любая неопределённость решается самостоятельно: выбрать разумный вариант, записать в `docs/DECISIONS.md` (дата, проблема, варианты, выбор, причина) и продолжить.
2. **Работать фазами.** Порядок фаз строгий. Переход к следующей фазе — только когда выполнены все *гейты* текущей фазы (см. ниже). Перед гейтом фаза не считается завершённой.
3. **Каждая фаза = отдельная ветка/серия коммитов + git-тег** `phase-N-done`. Коммиты маленькие, сообщения осмысленные (Conventional Commits).
4. **Файл `docs/PROGRESS.md`** — чек-лист всех фаз и задач. Обновлять после каждой завершённой задачи. В начале каждой новой сессии/после потери контекста первым делом читать `CLAUDE.md`, `docs/PROGRESS.md`, `docs/DECISIONS.md`.
5. **Файл `CLAUDE.md` в корне репозитория** — создать в фазе 0: краткие правила проекта, команды сборки/тестов, архитектурные ограничения, ссылка на этот план.
6. **Никаких заглушек в финале.** `TODO`, `FIXME`, закомментированный код, отладочные `Debug.Log` — не допускаются в релизной ветке (проверяется в фазе 11).
7. **Протокол «застрял».** Если задача не решается после 3 принципиально разных попыток: зафиксировать в `docs/DECISIONS.md`, выбрать упрощённый вариант, который не нарушает критерии MVP, и идти дальше. Остановиться полностью можно **только** при внешнем блокере (нет Unity, лицензии, SDK) — записать в `docs/BLOCKERS.md` точную причину и что нужно сделать.
8. **Сначала автоматическая проверка, потом уверенность.** Утверждение «работает» допустимо только если подтверждено тестом, ботом-игроком или логом сборки. Claude Code не может пощупать игру на телефоне — поэтому заменяет это симуляциями (см. раздел 4).
9. **Не добавлять функциональность вне MVP** (мультиплеер, магазин, реклама, достижения, онлайн-сервисы). Исключение: пункты из фаз 8–9, явно перечисленные ниже.
10. **Принцип GDD:** главный приоритет — качественная физика и приятное управление, а не количество тем и эффектов.

## 1. Предварительные условия (единственное, что нужно окружению до запуска)

Выполняются один раз человеком/окружением, **до** старта автономной работы. Claude Code проверяет их в фазе 0 скриптом `tools/preflight.sh`; при провале пишет `docs/BLOCKERS.md` и останавливается.

| Что | Проверка |
|---|---|
| Unity 6 LTS (или новейшая установленная LTS) с модулями Android Build Support, OpenJDK, Android SDK & NDK | переменная `UNITY_PATH` указывает на исполняемый файл; `$UNITY_PATH -version` работает |
| Активированная лицензия Unity (Personal достаточно) | пробный запуск `-batchmode -quit -nographics` завершается кодом 0 |
| Git, Python 3 (для генерации ассетов), `keytool` (из JDK) | `git --version`, `python3 --version`, `keytool -help` |
| (Linux/CI) `xvfb-run` для скриншотов с рендером | `xvfb-run --help` |

Что **заведомо нельзя** сделать автономно (Claude Code готовит всё, человек делает только финальный клик): создание аккаунта Google Play Console, загрузка `.aab`, прохождение закрытого тестирования (для новых личных аккаунтов Google требует его перед продакшеном — проверить актуальные правила), хостинг политики конфиденциальности по публичному URL. Claude Code обязан подготовить файлы и пошаговую инструкцию `docs/RELEASE_HANDOFF.md`.

## 2. Технические решения по умолчанию

- **Unity 6 LTS, 2D, URP 2D Renderer** (если проблемы с URP на целевых устройствах — Built-in 2D, зафиксировать в DECISIONS).
- **Input System** (пакет `com.unity.inputsystem`, `EnhancedTouch`).
- **Unity Test Framework**: EditMode + PlayMode тесты. Сборки `Assembly Definition` по модулям: `HR.Core`, `HR.Gameplay`, `HR.Input`, `HR.UI`, `HR.Themes`, `HR.Audio`, `HR.Save`, `HR.Tests.EditMode`, `HR.Tests.PlayMode`.
- **Рендер колец — процедурная геометрия**: сегмент дуги строится как `Mesh` (внутренний/внешний радиус, угол, опциональные закруглённые концы как на `ref_minimal`). Спрайты колец не используются — это даёт любую толщину/количество сегментов без артов.
- **Физика**: кольца — kinematic `Rigidbody2D` (вращение через `MoveRotation` в `FixedUpdate`), шарик — dynamic `Rigidbody2D` + `CircleCollider2D`, `CollisionDetectionMode2D.Continuous`, `Interpolate`. Фиксированный шаг подобрать в фазе 1 (60 или 90–120 Гц), ограничить максимальную скорость шарика и максимальную угловую скорость колец, чтобы исключить туннелирование.
- **Данные/настройки**: `ScriptableObject` — `GameConfig`, `DifficultyCurve`, `ThemeData`. Никаких «магических чисел» в коде.
- **Сохранения**: JSON в `Application.persistentDataPath`, версия схемы, безопасная загрузка повреждённого файла.
- **Монетизация и сети**: в v1.0 **отсутствуют** (нет рекламы, нет аналитики, нет разрешения INTERNET). Это упрощает Data Safety и политику конфиденциальности.
- **Ориентация**: только портрет. Поддержка разных соотношений сторон и вырезов (safe area).
- **Локализация**: RU + EN, простой собственный словарь (`Localization` + JSON/ScriptableObject), без тяжёлых пакетов.
- **Цель**: Android, minSdk 24 (или ниже, если даёт Unity 6), IL2CPP, ARM64 (+ARMv7 если не мешает), `.aab`. Target API — **актуальный требуемый Google Play на дату релиза** (проверить в документации, зафиксировать в DECISIONS).

### Механика по умолчанию (уточнение GDD, т.к. там есть неоднозначности)

Записать в `docs/MECHANIC.md` в фазе 0 и реализовать в фазах 1–3. Отклоняться можно только через DECISIONS и при условии прохождения гейтов.

- Кольца **концентрические** вокруг общего центра. Шарик находится в полости между кольцами, на него действует гравитация вниз.
- У каждого кольца 1 отверстие (на старте) — в поздней игре 1–2 отверстия меньшей ширины. Кольцо = несколько дуговых сегментов, зазор между ними = отверстие.
- Шарик опирается на нижнюю дугу ближайшего внешнего кольца. Игрок вращает кольца так, чтобы отверстие оказалось под шариком; шарик проваливается наружу сквозь отверстие и **оказывается в следующей полости** — это и есть «прохождение кольца» (+1 очко).
- Все кольца **равномерно сжимаются к центру** (радиус уменьшается во времени); визуально — эффект тоннеля, как на `ref_neon` (толщина и яркость растут с радиусом). Кольцо, радиус которого упал до минимума, удаляется в пул; новые кольца появляются на внешней стороне.
- Камера плавно следует за шариком и подбирает масштаб так, чтобы в кадре помещались ~4–6 ближайших колец, а шарик был в читаемой зоне экрана (вертикальный портрет).
- **Условие проигрыша**: шарик раздавлен — то есть сжимающееся кольцо/колец стало нечем пропустить шарик и зазор полости стал меньше диаметра шарика (измерять геометрически, а не только по коллизиям). Дополнительно — выход шарика за допустимую область.
- Допустимо мягкое наказание за касание (отскок), но не мгновенная смерть от обычного столкновения — только от раздавливания.

## 4. Стратегия автоматического контроля качества (вместо «пощупать на телефоне»)

1. **Юнит-тесты (EditMode):** математика колец, генератор, кривая сложности, сохранения, локализация, подсчёт очков.
2. **PlayMode-тесты:** шарик падает через отверстие; шарик не проваливается сквозь сегмент; вращение не ломает физику; пул не растёт; рестарт 50 раз подряд не копит объекты и не даёт ошибок.
3. **Бот-игрок (`BotPlayer`)** — главный инструмент оценки играбельности. Бот имитирует палец: задержка реакции, ограниченная угловая скорость жеста, шум. Параметры «слабого», «среднего», «сильного» бота. Бот работает через тот же `InputController`/тестовые touch-события, а не напрямую крутит кольца.
4. **Симуляции сложности (headless):** прогон тысяч попыток ботами с разными сидами → таблица «медианное число пройденных колец / доля непроходимых ситуаций». Результаты в `docs/BALANCE_REPORT.md`.
5. **Нагрузочные тесты:** замер кадра/GC на максимуме колец; отсутствие аллокаций в игровом цикле (профилировать `GC.Alloc` в PlayMode через `Recorder`/`ProfilerRecorder`).
6. **Визуальная проверка:** автоскриншоты (`tools/screenshots.sh`, через `xvfb-run` при отсутствии дисплея) для каждой темы и экрана в 4–5 разрешениях/пропорциях; Claude Code сам просматривает изображения и проверяет контраст, читаемость, safe area, перекрытие UI.
7. **Статическая гигиена:** сборка без ошибок и предупреждений компилятора; поиск `TODO|FIXME|Debug.Log` скриптом.

Все команды (`tools/run_tests.sh`, `tools/build_android.sh`) вызывают Unity в `-batchmode` и возвращают ненулевой код при провале.

## 5. Фазы

Для каждой фазы: **Задачи → Артефакты → Гейты (обязательные критерии завершения)**.

### Фаза 0. Bootstrap и решения
**Задачи**
- Создать Unity-проект (2D/URP, Unity 6 LTS), `.gitignore`, `.gitattributes` (Unity YAML merge/LFS для крупных бинарников при необходимости).
- Положить GDD и референсы в `docs/`. Написать `CLAUDE.md`, `PROGRESS.md` (все фазы и задачи чек-листом), `DECISIONS.md`, `MECHANIC.md` (раздел «Механика по умолчанию» уточнить числами: стартовый радиус, число колец в кадре, ширина отверстия в градусах, гравитация, диаметр шарика).
- Настроить Assembly Definitions, Input System, Test Framework, настройки Player (портрет, имя, идентификатор пакета `com.<studio>.hypnoticrings` — выбрать и зафиксировать).
- Написать `tools/preflight.sh`, `tools/run_tests.sh`, `tools/build_android.sh` (пока можно собирать development-билд).
- Настроить Editor-скрипт `SceneBuilder` и пустые сцены `Boot`, `Main`.
**Гейты**
- `preflight.sh` проходит; пустой проект собирается в Android APK командной строкой; `run_tests.sh` запускает тестовый пример и возвращает 0.

### Фаза 1. Физический прототип (GDD этап 1)
**Задачи**
- `RingMeshBuilder`: процедурная дуга (внутренний/внешний радиус, начальный угол, длина, шаг тесселяции, опциональные скруглённые концы).
- `RingSegment`, `RingController`: кольцо из N сегментов с отверстием заданной ширины (в градусах), kinematic вращение.
- `BallController`: dynamic `Rigidbody2D`, материал физики (трение/отскок), ограничение скорости.
- **Бенчмарк способов сжатия колец** и выбор лучшего по стабильности и стоимости: (A) масштабирование трансформа, (B) пересчёт точек коллайдеров в `FixedUpdate`, (C) пересоздание коллайдеров по шагам радиуса. Результат и обоснование — в DECISIONS.
- Подобрать фиксированный шаг физики, `Continuous` коллизии, пределы скорости.
**Артефакты:** сцена-песочница `Sandbox`, тесты.
**Гейты**
- PlayMode: шарик, стоящий на кольце, не проваливается; при совмещении отверстия — проходит; на 1000 прогонов со случайными скоростями вращения (до максимума) — 0 случаев туннелирования сквозь сплошной сегмент; ширина отверстия, равная диаметру шарика ×1.2, проходима.
- Нет аллокаций на кадр в стационарном режиме.

### Фаза 2. Управление (GDD этап 2)
**Задачи**
- `InputController`: угол касания относительно центра тоннеля → угловая дельта → скорость вращения всех активных колец; чувствительность, максимальная угловая скорость, инерция после отпускания, инверсия направления (настройки в `GameConfig`).
- Учёт мультитача (использовать первый палец), обрезка при выходе за экран, корректная работа при паузе/потере фокуса.
- Редактор-ввод: мышь для отладки; в тестах — симуляция touch через `InputTestFixture`.
**Гейты**
- PlayMode-тесты на жесты (по часовой / против часовой / резкий рывок / отпускание с инерцией / касание у самого центра — без деления на ноль и скачков).
- Бот через `InputController` стабильно проводит шарик через 1 кольцо ≥ 99% попыток при комфортных параметрах.

### Фаза 3. Бесконечный тоннель (GDD этап 3)
**Задачи**
- `RingSpawner` с **Object Pooling** (кольца и сегменты, меши переиспользуются, без `Instantiate/Destroy` в цикле).
- Сжатие колец к центру, удаление/возврат в пул, появление новых колец снаружи, согласованное с камерой.
- Регистрация прохождения (событие `OnRingPassed`), активное кольцо, камера: плавное следование и подбор масштаба (`CameraRig`).
- Эффект глубины: толщина/альфа/цвет зависят от радиуса (как на `ref_neon`); реализовать в `ThemeApplier`/шейдере простого материала.
- Генератор `RingGenerator` с сидом (детерминизм), **проверка достижимости** следующего прохода (см. фазу 4).
**Гейты**
- 10 000 прохождений ботом подряд без роста количества объектов, без утечек памяти (сравнение `Profiler`/`GC.GetTotalMemory` в начале/конце в допуске), без исключений.
- Количество активных колец ограничено конфигом.

### Фаза 4. Сложность, счёт, состояния игры (GDD этап 4)
**Задачи**
- `GameManager` (конечный автомат: Boot → Menu → Playing → Paused → GameOver), `ScoreManager`, `DifficultyManager` (кривая `DifficultyCurve`: скорость сжатия, скорость вращения, ширина отверстия, число отверстий, расстояние между кольцами, сочетание направлений вращения соседних колец).
- Условие проигрыша (раздавливание) — по геометрии, детерминированно, без ложных срабатываний.
- Рестарт с полной очисткой состояния.
- **Генератор достижимости**: для каждого нового кольца вычислять минимальное угловое расстояние до отверстия и требуемую угловую скорость; если требуется больше `maxHumanSpeed × safetyFactor`, генератор пересаживает отверстие. Формулы — в `docs/BALANCE.md`.
**Гейты**
- Симуляция 5 000 попыток ботами каждого уровня: 0 непроходимых колец (по формуле и по факту у «сильного» бота без шума); «средний» бот в среднем проходит 25–60 колец, «слабый» — 8–20 (диапазоны можно уточнить, но кривая обязана быть монотонной и без скачков >15% между соседними кольцами). Отчёт `docs/BALANCE_REPORT.md` с графиками (png, строить matplotlib).
- Тест рестарта ×50: нет накопления объектов и ошибок.

### Фаза 5. Визуальные темы (GDD этап 5)
**Задачи**
- `ThemeData` (ScriptableObject): цвета фона/колец (палитра по глубине)/шарика/UI/счёта, толщина линий, форма концов сегментов (скруглённые как `ref_minimal` или прямые как `ref_neon`), режим цвета колец (один цвет / чередование / градиент по глубине), опциональные эффекты.
- `ThemeManager`: применение темы без перезагрузки сцены и без влияния на физику (проверить тестом: хэш физических параметров не меняется при смене темы).
- Темы MVP: **Monochrome** (по `ref_minimal`), **Midnight** (тёмный фон), **Neon** (по `ref_neon`: тёмно-синий фон, синие/жёлтые/фиолетовые кольца, сиреневый шарик). Остальные (Pastel, Earth) — готовы как данные, включены в релиз, если проходят проверку контраста.
- Автопроверка контраста (WCAG-подобный расчёт отношения яркостей шарик/кольцо/фон ≥ 3:1) как EditMode-тест для каждой темы.
**Гейты**
- Автоскриншоты всех тем в 3 пропорциях; Claude Code визуально сверяет с референсами и фиксирует результат в `docs/VISUAL_REVIEW.md`.

### Фаза 7. Звук (GDD этап 6, часть 2)

### Фаза 9. Тестирование и оптимизация (GDD этап 7)
**Задачи**
- Полный прогон EditMode + PlayMode; расширить тесты до целевого покрытия критичной логики (генератор, сложность, сохранения, жесты, состояния игры).
- Производительность: цель — стабильные 60 FPS на среднем Android (эмулировать ограничение через упрощённый профиль); 0 `GC.Alloc` в игровом кадре; мешы колец не пересоздаются без необходимости; draw calls минимальны (батчинг/один материал на тему).

- Long-run soak: 30 минут симуляции бота — память стабильна.
**Гейты**
- Все тесты зелёные; `docs/PERF_REPORT.md` с цифрами; нет предупреждений при сборке; размер в целевом коридоре (или обоснованное отклонение в DECISIONS).

## 7. Реестр рисков и заранее решённые развилки

| Риск | Решение |
|---|---|
| Нестабильная физика при вращающихся/сжимающихся коллайдерах | Бенчмарк способов в фазе 1; лимиты скоростей; Continuous; шаг 90–120 Гц; при необходимости упрощение до меньшего числа сегментов |
| Туннелирование шарика через тонкие кольца | Минимальная физическая толщина сегмента больше визуальной; ограничение скорости шарика и вращения; тесты на 1000+ прогонов |
| Невозможно проверить «ощущение» без телефона | Бот-симуляции + параметры в `GameConfig` + консервативные значения; человек может подкрутить конфиг после релиза без изменений кода |
| Нет аудио/графических ассетов | Всё процедурное: меши — код, звук — синтез, иконки — Pillow |
| Unity batchmode без GPU | `-nographics` для тестов; `xvfb-run` для скриншотов; если рендер невозможен — зафиксировать в BLOCKERS и сгенерировать скриншоты через RenderTexture в Editor-скрипте |
| Контекст сессии Claude Code исчерпан | `CLAUDE.md` + `PROGRESS.md` + `DECISIONS.md` — единственный источник правды; в конце каждой задачи обновлять |
| Требования Google Play меняются | В фазе 10/11 свериться с актуальной документацией (target API, Data Safety, правила для новых аккаунтов) и зафиксировать в DECISIONS |
| Раздувание объёма | Всё вне MVP — в `docs/BACKLOG.md`, не реализуется |
