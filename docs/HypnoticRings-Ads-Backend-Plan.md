# Hypnotic Rings — план рекламы (аккаунты, SDK, бэкенд)

Дата исследования: 5 ноября 2026. Источники в конце файла (§14).
Это план, в коде ничего из этого пока нет. Экраны и размеры берутся из
`HypnoticRings-UI-Reference.md` (§5.7 «Ads», §5.8 «Countdown», §15.x, §17).

**Версия 2 (5 ноября 2026)** — сверена с макетом. Что изменилось: раскладка Pause / Game over
пересчитана, зазоры «реклама ↔ карточка» подняты до 64, добавлены подписи «Реклама»,
фолбэки по состоянию загрузки, строка «Параметры конфиденциальности», шаг UMP при старте,
позиция баннера по координатам. Устаревшие места (резерв под баннер в Playing,
`CardInset = bannerHeight + 48`) удалены.

**Как читать (для агента-исполнителя).** Два файла работают вместе:
`HypnoticRings-UI-Reference.md` — *что рисовать* (размеры, wireframe, строки, тесты);
этот файл — *как подключать рекламу и по каким правилам*. Если числа расходятся, источник правды
по раскладке рекламы — **UI-Reference §5.7**, по всему остальному (SDK, согласие, состояния,
флаги) — этот файл. Закрытые вопросы перечислены в §0a, их не переоткрывать.
Шрифты, темы и визуальные эффекты — UI-Reference §18 (рекламу они не затрагивают, кроме того, что подпись «Реклама» набирается Manrope Medium, а цвета берутся из активной темы).

«Бэкенд рекламы» здесь = всё, что стоит **за** кнопками и слотами: аккаунты,
SDK, согласие пользователя, загрузка/показ, состояния игры, тесты. Собственный
сервер **не нужен** (см. §8, SSV).

## 0. Главное, что нужно знать до начала

| # | Факт | Что это значит для нас |
|---|---|---|
| 1 | В гайдах AdMob по баннерам прямо сказано: баннер не стоит ставить на **игровой экран, где пользователь постоянно взаимодействует**, и рядом с интерактивными кнопками. Формально это «не рекомендуется», а не «запрещено», но Google оставляет за собой право отключить показ рекламы в приложении при невалидных кликах | Баннер во время игры (круговые свайпы по экрану, баннер внизу) — **самое рискованное решение в дизайне**. Делаем его флагом `bannerInPlay`, чтобы выключить без релиза кода (§6, §9) |
| 2 | Тот же гайд для 300×250: на экране паузы / конца уровня он **может быть допустим**, если пользователя не вынуждают и не обманом заставляют кликнуть по рекламе, и реклама визуально отделена от кнопок. Отдельно: реклама не должна «висеть поверх контента», в том числе поверх фона, который закрывает контент приложения | Наш MREC лежит на затемнённой замороженной сцене и в 24 единицах от карточки с кнопками. Оба момента спорные (§9) |
| 3 | Адаптивный баннер имеет высоту от 50 dp до 90 dp (не больше 15 % высоты экрана) | В схемах баннер = 150 единиц канваса (= 50 dp). Адаптивный баннер может быть до ~270 единиц и **сломает бюджет высоты game over**. Берём фиксированный `AdSize.Banner` 320×50 (§5) |
| 4 | Google Play с 31.08.2026 требует для новых приложений и обновлений **target API 36** | Нужен Unity не ниже **6000.0.46f1** (так заявлено в доке Unity для API 36) (§3) |
| 5 | Личный аккаунт Play, созданный после 13.11.2023, обязан до выхода в production провести **закрытый тест: 12 тестеров, 14 дней подряд** | Это самый длинный пункт критического пути. Начинать надо сразу (§2, §12) |
| 6 | Деньги: порог первой выплаты 100 USD (или эквивалент), выплата около 21-го числа следующего месяца, перед этим верификация личности и PIN-письмо по почте | Реальные деньги не раньше чем через несколько недель после набора порога (§2.6) |
| 7 | Unity Ads напрямую (пакет Advertisement Legacy) больше не рекомендуется: с 31.01.2026 Unity Ads работает только через in-app bidding, то есть через LevelPlay | Если когда-нибудь нужен Unity Ads, то только через пакет Ads Mediation / LevelPlay (§1) |

## 0a. Принятые решения (не переоткрывать)

| # | Решение | Где зафиксировано |
|---|---|---|
| D1 | На Pause и Game over остаются **и баннер, и MREC** (уровень B). Баннер только там; в Countdown / Playing / Menu / Themes / Settings рекламы нет | §4.3, §9 |
| D2 | Место набирается за счёт **отступов**, ничего из UI не убирается: плашка счёта 232 → 200, паддинги карточки (Pause 48 → 24, Game over → 8), спейсинг карточки Game over 24 → 16, `ЕЩЁ РАЗ` 210 → 150 | UI-Reference §5.7, §15.3, §15.4 |
| D3 | Зазор «реклама ↔ плашка карточки» = **64** (цель), **48** — жёсткий нижний предел, до него зазоры сжимаются перед отказом от MREC | UI-Reference §5.7 |
| D4 | Подпись **«Реклама» / «Ad»** над каждым слотом (баннер, MREC). Лежит **вплотную над слотом, не поверх рекламы** (наложение на рекламу — лишний риск, места хватило без него) | UI-Reference §5.7 |
| D5 | Раскладка Pause / Game over **выбирается один раз при показе экрана**. Слот, не загрузившийся к этому моменту, считается отсутствующим; поздняя загрузка игнорируется до следующего показа (нет прыжка раскладки) | §4.3, UI-Reference §5.7 |
| D6 | Порядок сжатия: flex-зазор → минимум; зазоры 64 → 48; затем отказ от MREC и **старая раскладка** (счёт и рекорд внутри карточки, `ЕЩЁ РАЗ` 210) | UI-Reference §5.7 |
| D7 | Игра, открывшая тему: **старая раскладка** без MREC (строка «Открыта тема…» внутри карточки) | UI-Reference §15.4 |
| D8 | Баннер ставится **по координатам от низа safe area**, а не `AdPosition.Bottom` | §5.1 |
| D9 | Форма UMP при старте **не блокирует** меню: меню строится сразу, форма поверх него; пока согласия нет — реклама выключена, игра полностью играбельна | §4.2, UI-Reference §17 |
| D10 | Строка «Параметры конфиденциальности» в Settings существует **только** если UMP требует (`PrivacyOptionsRequirementStatus == Required`) | §7.1, UI-Reference §5.6 |
| D11 | Rewarded: одно продолжение на забег, normal и hardcore; награда выдаётся **после закрытия** рекламы | §4.4 |
| D12 | v1 только AdMob, без медиации и без своего сервера | §1, §8 |
| D13 | Визуальная идентичность: пара шрифтов Unbounded Bold + Manrope Medium, семь тем в карусели (Minimal светлая/тёмная как одна, Neon cosmos, Art deco, Sumi-e, Deep ocean, Bauhaus, Retro CRT) и скин хардкора Ember, фоновые эффекты, новые пороги открытия и миграция сохранённой темы | UI-Reference §18 |

## 1. Выбор рекламной платформы

| | **AdMob + Google Mobile Ads Unity Plugin** | **Unity LevelPlay (Ads Mediation)** |
|---|---|---|
| Что это | Реклама от Google, одна сеть | Медиация: аукцион между несколькими сетями (в т.ч. Unity Ads) |
| Аккаунт | AdMob (Google-аккаунт) | LevelPlay (аккаунт Unity), ручная настройка сетей, инстансов, mediation groups |
| Форматы под нас | Banner, MREC (`AdSize` 300×250), Rewarded | Banner (в т.ч. MEDIUM_RECTANGLE), Rewarded, Interstitial |
| Сложность старта | Ниже | Выше (больше панелей и настроек) |
| Тест-режим | Тестовые ad unit ID Google + тестовые устройства | Test Suite внутри SDK, приложение остаётся в test mode, пока не выключите в дашборде |
| Выплаты | Через AdMob | Через LevelPlay / выбранные сети |

**Рекомендация для v1: только AdMob.** Один аккаунт, один SDK, три ad unit.
Медиацию можно добавить позже, не меняя игровой код, если слой рекламы изолирован
за интерфейсом (§4). Документация AdMob для Unity отдельно описывает подключение
Unity Ads и ironSource как источников внутри AdMob-медиации, так что путь расширения есть.

Платформа: **Android** (в UI уже есть `AndroidBackButton`). iOS позже: нужны
Xcode 16+, CocoaPods, iOS 13+, ATT-диалог и отдельный AdMob-app для iOS.

## 2. Аккаунты и привязки — по порядку

Порядок важен: часть шагов ждёт других.

```
[Google-аккаунт для разработчика]  ← один долгоживущий, не «одноразовый»
        │
        ├─▶ 2.1 Google Play Console  ($25, ID + карта на ваше имя)
        │        └─ личный аккаунт → закрытый тест 12 чел × 14 дней
        │
        ├─▶ 2.2 AdMob аккаунт        (страна нельзя изменить позже)
        │        ├─ телефон, платёжные данные, верификация (24 ч … 2 недели)
        │        └─ 2.3 регистрация приложения + ad units
        │
        ├─▶ 2.4 Сайт разработчика + app-ads.txt (после публикации в Play)
        ├─▶ 2.5 Privacy & messaging (UMP) + политика конфиденциальности
        └─▶ 2.6 Выплаты: порог → личность → PIN → способ оплаты → 100 USD
```

### 2.1 Google Play Console

- Армения есть в списке стран, где можно зарегистрироваться разработчиком и
  мерчантом (валюта по умолчанию USD).
- Единоразовый взнос $25. Могут запросить документ с фото и банковскую карту, обе
  вещи на ваше юридическое имя. Если данные признают недействительными, взнос не возвращается.
- Тип аккаунта: **личный или организация**, конвертировать нельзя. Организация
  (с D-U-N-S) освобождена от правила 12 тестеров. Личный аккаунт, созданный после
  13.11.2023, должен провести закрытый тест с ≥12 тестерами, подписанными непрерывно
  14 дней, и только потом подать заявку на production. Требование **на каждое приложение**.
- Мерчант-аккаунт (для платных приложений и покупок) для бесплатной игры с рекламой
  **не нужен**.
- Нужно: приложение (AAB), иконка, скриншоты, описание, контент-рейтинг, Data safety,
  Ads declaration, Target audience, App access, политика конфиденциальности (URL).
- Target API 36 для новых приложений и обновлений (§3).

### 2.2 AdMob аккаунт

1. https://admob.google.com → войти тем же Google-аккаунтом.
2. Выбрать страну проживания: **изменить позже нельзя**. Таймзона и валюта аккаунта тоже фиксируются.
3. Подтвердить телефон (SMS или голосовой звонок).
4. Ввести платёжные данные: имя, тип (индивидуальный/организация), адрес.
   Верификация обычно до 24 часов, редко до 2 недель. Пока аккаунт не подтверждён,
   показывать рекламу нельзя.
5. Армения входит в список регионов, где можно зарегистрироваться в AdMob.
   Санкционные ограничения касаются Крыма, Кубы, «ДНР/ЛНР», Ирана, КНДР.

### 2.3 Приложение и ad units в AdMob

1. Apps → Add app → Android. Если игры ещё нет в Play, выбрать «нет в магазине»,
   привязать позже.
2. Записать **App ID** (`ca-app-pub-…~…`). Он идёт в Unity Settings (§3).
3. Создать три ad unit (имена для порядка):

   | Имя | Формат в AdMob | Где в игре | Размер |
   |---|---|---|---|
   | `hr_banner_bottom` | Banner | Paused / GameOver | 320×50 |
   | `hr_mrec_overlay` | Banner (размер 300×250 задаётся в коде) | Paused / GameOver | 300×250 |
   | `hr_rewarded_continue` | Rewarded | кнопка «▶ Продолжить · реклама» | — |

   Для rewarded в AdMob задаётся награда (название и количество). Мы её в коде
   игнорируем: награда = «одно продолжение».
4. После публикации в Play: привязать приложение к листингу (AdMob сам найдёт его по
   package name; следить, чтобы package совпал).
5. Записать все ID в таблицу и **не коммитить** в публичный репозиторий боевые ID
   без нужды (они не секрет, но лишний повод для чужого трафика). Тестовые ID см. §10.

### 2.4 Сайт разработчика и app-ads.txt

- В Play Console в контактных данных листинга указывается сайт разработчика.
  AdMob берёт домен оттуда и ищет `https://<домен>/app-ads.txt`.
- Файл кладётся в корень сайта. Содержимое берётся из AdMob (строка вида
  `google.com, pub-XXXXXXXXXXXXXXXX, DIRECT, f08c47fec0942fa0` — точный текст копируем
  из панели AdMob, не из памяти).
- Проверка AdMob занимает до 24 часов. Файл защищает от подмены приложения и
  нужен, чтобы рекламодатели доверяли инвентарю.
- Сайт может быть минимальным: страница игры + страница политики конфиденциальности.
  Политика всё равно нужна для Play.

### 2.5 Privacy & messaging

- В AdMob → Privacy & messaging создать сообщение (GDPR / consent). UMP SDK
  показывает его по App ID.
- Размещённую политику конфиденциальности привязать к листингу и к экрану «Об игре».
- Подробности реализации в игре: §7.

### 2.6 Выплаты (последовательность)

1. Заработок достигает **$10** → начинается подтверждение личности.
2. Подтверждение личности: документы нужно загрузить в течение **45 дней**
   с первого запроса, иначе показ рекламы и выплаты останавливаются.
3. Почтовый **PIN** на адрес из платёжного профиля (по стандартной почте, до 2–3
   недель); ввести в аккаунте в течение **4 месяцев** с момента генерации.
4. При достижении порога выбора способа оплаты → Payments → «Add payment method».
5. Порог выплаты **$100** (или эквивалент). Баланс за месяц фиксируется в начале
   следующего, выплата примерно 21-го числа, если нет блокировок.
6. Налоговая информация — если AdMob запросит для вашей страны.
7. Способы оплаты зависят от платёжного адреса (чек, EFT, wire, SEPA). Для Армении
   в таблице AdSense (а не AdMob) указаны чек и wire, EFT нет. **Надо проверить в самом
   AdMob** (Payments → Add payment method), когда дойдёт до порога. Менять платёжные
   данные нужно до 21-го числа, иначе изменения вступят в силу в следующем цикле.

## 3. Настройка Unity-проекта

| Параметр | Значение | Откуда |
|---|---|---|
| Unity Editor | **≥ 6000.0.46f1** (API 36); для 16-KB страниц памяти ≥ 6000.0.38f1 | доки Unity |
| Плагин | Google Mobile Ads Unity Plugin: OpenUPM (`com.google.ads.mobile`, scope `com.google` на `https://package.openupm.com`) или `.unitypackage` с GitHub | доки AdMob |
| Минимальный Android API | **24** | доки AdMob |
| Target Android API | **36** (Play с 31.08.2026); плагин требует ≥ 35 | Play, AdMob |
| Менеджер зависимостей | External Dependency Manager (ставится вместе с плагином; можно отключить, если зависимости собираются вручную) | доки AdMob |
| App ID | Unity: Assets → Google Mobile Ads → Settings, поле Android. Сохраняется в `Assets/GoogleMobileAds/Resources/GoogleMobileAdsSettings.asset` | доки AdMob |
| Android SDK движка рекламы | Можно включить GMA **Next-Gen SDK** (меньше задержки, лучше стабильность): в тех же Settings включить «Switch Google Mobile Ads Android Architecture» и «GMA Next-Gen SDK». На старых версиях плагина правится `GoogleMobileAdsDependencies.xml` | доки AdMob |
| Сборка | Тестировать только на **реальном устройстве**: эмуляторы Android Unity не поддерживает | доки Unity |

Шаги:

1. Обновить Unity до нужной версии, проверить сборку **без** рекламы под API 36.
2. Поставить плагин, прописать App ID (пока можно тестовый, §10).
3. Resolve → собрать пустой проект на устройство.
4. Настроить манифест: разрешение на рекламный ID. Если не хотим собирать
   advertising ID, это делается правкой манифеста (см. Play-раздел Data safety,
   §7); но тогда падает эффективность рекламы.

**Важно для архитектуры.** Правило из `HypnoticRings-UI-Reference.md` §13: `HR.Core`
не должен ссылаться на `UnityEngine`. Поэтому реклама делится на сборки так:

```
HR.Core    IAdService, AdSlotId, AdEvents, AdState, RunSnapshot
           (чистый C#, тестируется без Unity)
HR.Ads     GoogleAdService : IAdService   ← единственное место с GoogleMobileAds.*
           NullAdService   : IAdService   ← редактор, тесты, «no ads»
HR.UI      читает AdInsets из IAdService, строит слоты
```

## 4. Архитектура

### 4.1 Интерфейс (набросок)

```csharp
// HR.Core — без UnityEngine
public enum AdSlot { Banner, Mrec }

public interface IAdService
{
    bool CanRequestAds { get; }                    // после согласия
    bool RewardedReady { get; }
    event Action<AdSlot, bool> SlotLoadedChanged;  // слот загрузился / пропал
    event Action RewardedEarned;
    event Action RewardedClosed;

    void Initialize(Action done);                  // UMP → Initialize → preload
    void ShowBanner(bool visible);
    void ShowMrec(bool visible);
    bool TryShowRewarded();                        // false, если не готова
    AdInsets GetInsetsInCanvasUnits(float canvasScaleFactor);
    void OpenPrivacyOptions();                     // для Settings
    bool PrivacyOptionsRequired { get; }
}
```

### 4.2 Запуск

```
App start
 └─ ConsentInformation.Update(...)              каждый запуск, не кешировать
     └─ ConsentForm.LoadAndShowConsentFormIfRequired(...)
         └─ ConsentInformation.CanRequestAds() ?
              ├─ да  ─▶ MobileAds.Initialize ─▶ preload Banner, MREC, Rewarded
              └─ нет ─▶ реклама выключена в этой сессии (слоты схлопнуты)
```

- `CanRequestAds()` всегда `false` до вызова `Update()`.
- Если при согласии произошла ошибка, всё равно проверить `CanRequestAds()`: SDK
  использует статус из прошлой сессии.
- Флаги запроса (например `tagForChildDirectedTreatment`) надо ставить **до**
  `MobileAds.Initialize()`. Мы не детская игра, но эту строку надо проверить при
  выборе Target audience.
- Все колбэки SDK приходят в **фоновом потоке**. Всё, что трогает UnityEngine,
  оборачиваем в `MobileAdsEventExecutor.ExecuteInUpdate(...)`.

### 4.3 Состояния слотов

| Слот | Когда грузим | Когда показываем | Когда прячем |
|---|---|---|---|
| Banner | после согласия, один раз | **Paused, GameOver** | Countdown, Playing, Menu, Themes, Settings; на время fade-out Curtain |
| MREC | после согласия; перезагрузка после каждого показа | Paused, GameOver (если хватает высоты) | при выходе с этих экранов; на время rewarded |
| Rewarded | на старте и сразу после каждого закрытия | кнопка «▶ Продолжить · реклама» на GameOver | — |

Правила:

- Баннер скрываем (`Hide`), а не уничтожаем при смене экранов, чтобы не терять
  загрузку. Уничтожать (`Destroy`) только при выключении рекламы.
- Баннер показываем только на Paused/GameOver, на старте забега (Countdown) он скрыт. Показываем баннер **после** конца fade-in Curtain (0.35 s), скрываем на **начале**
  fade-out: Curtain не закрывает нативные view (§15.0).
- **Раскладка выбирается один раз при показе Pause / GameOver** (D5). Для этого `IAdService`
  отдаёт на момент показа: `BannerLoaded`, `MrecLoaded`, `RewardedReady` и реальные высоты в единицах
  канваса. Алгоритм (flex-зазор, порядок сжатия, старая раскладка) — UI-Reference §5.7, чистая функция
  в `HR.Core`.
- Подпись «Реклама» — обычный Canvas-текст экрана (не часть нативного view); она появляется и исчезает
  вместе со своим слотом. Видимость слота и подписи всегда меняются одним действием.
- Автообновление баннера настраивается в AdMob. Не перезапрашивать чаще
  примерно раза в минуту.
- Rewarded одноразовый: после показа объект нельзя использовать, нужен новый `Load`.
  Загруженная реклама «протухает» примерно через час, поэтому кэш обновляется.
- Загрузку после ошибки повторять с ограничением (backoff, максимум N попыток),
  не в бесконечном цикле.

### 4.4 Реворд-продолжение (последовательность)

```
Смерть
 ├─ снимок: score, tempo (скорость колец и спавн), расположение колец,
 │          флаги «уже тронуто» (хардкор), режим (normal / hardcore)
 └─ GAMEOVER   кнопка видна ⇔ RewardedReady && continuesUsed == 0 && adsEnabled

Нажали «▶ Продолжить · реклама»
 ├─ TryShowRewarded()  → false: кнопка исчезает, остаёмся на GAMEOVER
 ├─ OnAdFullScreenContentOpened : заглушить звук/музыку, остановить время,
 │                                выключить Android Back
 ├─ reward callback             : rewardEarned = true   (только флаг!)
 ├─ OnAdFullScreenContentFailed : rewardEarned = false → GAMEOVER
 └─ OnAdFullScreenContentClosed : вернуть звук и время, перезагрузить rewarded
        ├─ rewardEarned → continuesUsed++ → COUNTDOWN (RunSnapshot) → PLAYING
        └─ иначе        → GAMEOVER, кнопка исчезает
```

Наблюдения:

- Награду выдаём **после закрытия**, а не в reward-колбэке: колбэк может прийти раньше
  закрытия, и перезапускать игру под рекламой нельзя.
- Если пользователь свернул приложение во время рекламы, на возврате состояние должно
  быть консистентным (рекламу закрыл SDK, звук и время вернулись).
- Счётчик `continuesUsed` живёт в `RunState`, не сохраняется на диск. Новый забег
  («ЕЩЁ РАЗ» / из меню) обнуляет его.
- Хардкор: продолжение разрешено. Убийца-кольцо убирается, остальные сохраняют флаги,
  сплошное кольцо новое (решено в UI-reference §5.8).
- Best / unlock проверяются при каждой смерти, дубликаты разрешены (решено).

### 4.5 Новые состояния игры

`GameState`: добавить `Countdown`. Переходы: `Menu → Countdown → Playing`,
`GameOver → (reward) → Countdown → Playing`, `GameOver → «ЕЩЁ РАЗ» → Countdown → Playing`.
Во время `Countdown` не принимаем пауза/ввод/Back.

## 5. Интеграция в раскладку UI

Подробные размеры, wireframe и бюджет высоты — **UI-Reference §5.7, §15.3, §15.4**. Здесь только то,
что нужно знать при подключении SDK.

### 5.1 Размеры слотов и позиция

- Размер в px берётся у `BannerView`; перевод в единицы канваса: `units = px / canvas.scaleFactor`.
  На экране шириной 1080 px (`scaleFactor` = 1) баннер 320×50 dp = 150 единиц, MREC 300×250 dp = 750.
  На других экранах числа иные (на 20:9 `scaleFactor` ≈ 1.12), поэтому **константы 150 и 750 из схем —
  это референс, раскладка считается по реальным высотам**.
- Только фиксированный `AdSize.Banner` (320×50), не адаптивный (50–90 dp): иначе бюджет высоты плавает.
- Высота MREC (300×250 dp) тоже считается из px.
- **Позиция баннера — по координатам, не `AdPosition.Bottom`** (D8). Конструктор
  `BannerView(adUnitId, adSize, x, y)`; `y` считается от **нижней границы safe area** (последние
  150 единиц safe area), а не физического края экрана. Единицы `x`/`y` в плагине (dp или px) —
  **проверить на устройстве** (§13) и перевести из единиц канваса.
- Нижний инсет (жестовая панель) и вырез учитывает `SafeAreaFitter`; рекламные view позиционируются
  относительно того же прямоугольника.

### 5.2 Что меняется в коде UI

- `AdInsets { BannerHeight, MrecHeight }` (в единицах канваса) приходит из `IAdService`; жёстких чисел
  150 / 750 в UI-коде быть не должно.
- Новые токены (UI-Reference §5.7): `AdGap` 64, `AdGapMin` 48, `AdLabelSize` 28 (полоса 41),
  `AdScoreBand` 200, паддинги карточек Pause (24/24) и Game over (8/8, спейсинг 16).
- **Pause:** плашка непрозрачная (alpha 1.0), экран сам рисует счёт (плашка 200), ниже подпись + MREC,
  карточка (581), подпись + баннер. **Game over:** счёт и рекорд вынесены из карточки наверх, затем
  подпись + MREC, карточка только из кнопок (награда, `В меню | Темы`, `ЕЩЁ РАЗ` 150), подпись + баннер.
  Верх (счёт/рекорд) прижат к верху, низ (карточка, баннер) прижат к низу, весь остаток высоты уходит в
  один flex-зазор между ними.
- Когда MREC не помещается, не загрузился к моменту показа, выключен или забег открыл тему: старая
  раскладка (UI-Reference §15.4, фолбэки a–c). Баннер не загрузился: баннера и его подписи нет, нижний
  край карточки на `CardInset` (72) от низа safe area (фолбэк e). Кнопка награды скрыта: карточка
  короче на 166, остаток уходит во flex-зазор (фолбэк d).
- **Раскладка в Playing не меняется**: баннера там нет, место под него не резервируется, подсказка
  остаётся на 180–260 от низа.
- **Тесты раскладки** (UI-Reference §13): слоты и подписи добавляются в тест «ничего не налезает и не
  уходит под вырез» на всех соотношениях сторон и для всех комбинаций наличия слотов; зазор «слот ↔
  плашка карточки» ≥ 48 всегда и = 64, когда хватает высоты; подпись касается слота, но не пересекает.
  Порядок сжатия — чистая функция в `HR.Core`, тестируется без Unity.
- **Settings:** строка «Параметры конфиденциальности» (D10) увеличивает контент 1879 → 2045 только
  там, где UMP её требует. Экран и так скроллится на более квадратных экранах.

## 7. Приватность и документы

### 7.1 Согласие (UMP)

- Каждый запуск: `Update()` → `LoadAndShowConsentFormIfRequired()` → `CanRequestAds()`.
- Если сообщение требует точку входа «Параметры конфиденциальности», добавляем в
  Settings кнопку/ссылку: видна и активна, только когда
  `PrivacyOptionsRequirementStatus == Required`, и вызывает `ShowPrivacyOptionsForm()`. Раскладка строки: UI-Reference §5.6 / §15.6 (link-кнопка высотой
  150 между вторым и третьим спейсером; когда не требуется, в раскладку не добавляется вовсе, без зазора).
  Старт: форма показывается **поверх уже построенного меню** и не блокирует его (D9).
- Для теста в Европе: `ConsentDebugSettings` с `DebugGeography.EEA` и ID тестового
  устройства; `ConsentInformation.Reset()` для имитации «первой установки» (только
  в отладке).

### 7.2 Что нужно задекларировать в Play

- **Ads declaration:** «содержит рекламу» = да.
- **Data safety:** по документации AdMob SDK автоматически собирает и передаёт
  IP-адрес, взаимодействия с продуктом (запуск, нажатия, просмотры видео),
  диагностику, идентификаторы устройства и аккаунта (рекламный ID, app set ID) для
  рекламы, аналитики и защиты от мошенничества. Трафик шифруется TLS. Ответственность
  за форму лежит на разработчике.
- **Рекламный ID:** сбор опционален; отключается правкой манифеста, но влияет на доход.
- **Target audience:** игра не детская; выбрать возрастные группы без детей. Если
  когда-нибудь включать детей, это другая политика (Families) и другие настройки рекламы.

## 8. Чего делать не нужно

- **Свой сервер** — нет. Игра офлайн, валюты нет, наград, которые стоит защищать, нет.
- **Server-side verification (SSV)** — нужен для игр, где награда имеет ценность вне
  устройства (валюта, серверный профиль). Для одного продолжения в одиночной игре не
  нужен. Если когда-нибудь появится серверная валюта, SSV включается через
  `SetServerSideVerificationOptions` и проверку подписи на сервере.
- **Rewarded interstitial / App open / Native** — не планируем.
- **Interstitial** — в дизайне нет. Но это естественный «разрыв» (после game over
  каждые N игр) и запасной вариант, если баннер в игре придётся убрать (§9, уровень C).

## 9. Риски политики и запасные варианты

| # | Что в дизайне | Почему рискованно | Что можно сделать |
|---|---|---|---|
| R1 | Баннер на экране игры (Playing) — **снят из дизайна** | Гайд AdMob не рекомендует баннеры на игровом экране с постоянным вводом; плюс **свайп, начатый на баннере, съедается нативным view**, и это даёт случайные клики и баги управления | `bannerInPlay = false` |
| R2 | Баннер внизу, карточка с кнопками над ним — **зазор 64 (было 48)** | Правило «не рядом с интерактивными кнопками». 48 единиц ≈ 16 dp — мало; 64 ≈ 21 dp, до ближайшей кнопки 72–88 | Зазор 64 цель, 48 нижний предел (UI-Reference §5.7). Если и этого окажется мало по Policy center: убрать баннер на Pause/GameOver и оставить только MREC (уровень C) |
| R3 | MREC на затемнённой замороженной сцене — **исправлено: плашка непрозрачная** | «Реклама не должна висеть поверх контента, в том числе поверх фона, закрывающего контент». Для паузы/конца уровня 300×250 допустим, если не обманывает пользователя | Сделать фон экрана паузы/конца непрозрачной плашкой темы, а не затемнением сцены |
| R4 | MREC и карточка на Game over — **исправлено: зазор 64, бюджет высоты пересчитан** (счёт 200, паддинги 8, спейсинг 16, `ЕЩЁ РАЗ` 150, flex-зазор, порядок сжатия) | «Рядом с интерактивными элементами» | Реализовано в UI-Reference §15.4; в крайнем случае — старая раскладка без MREC |
| R5 | Реклама маркируется — **добавлена подпись «Реклама»** над баннером и MREC | Рекомендуют, чтобы реклама была отличима от контента | Подпись лежит в зазоре вплотную над слотом, **не накладывается на рекламу** (наложение — отдельный риск), без призыва к клику (D4) |
| R6 | Реворд: кнопка явная | Rewarded допустим, только если пользователь соглашается сам. У нас кнопка явная, с пометкой «реклама» | OK |

Уровни отката (переключаются флагами, без изменения логики):

- **A.** Баннер и в игре (Playing) + MREC + rewarded. Не рекомендуется.
- **B. (выбран)** Баннер только на Pause / GameOver + MREC + rewarded, плашки непрозрачные, зазоры ≥ 48.
- **C.** Без баннера. MREC на Pause/GameOver, rewarded, плюс interstitial после game over раз в N забегов.

Политика меняется; перед релизом прочитать актуальные страницы в «Policy center»
своего аккаунта AdMob.

### 10.1 Тестовые ad unit ID (Android, из доки AdMob)

| Формат | ID |
|---|---|

| Banner (адаптивный) | `ca-app-pub-3940256099942544/9214589741` |

MREC использует тестовый ID баннера. **Внимание:** в примере кода на странице Rewarded
в доке указан ID `…/1033173712`, это interstitial. Правильный ID для rewarded берём
из таблицы «Enable test ads» (`…/5224354917`).

### 10.2 Правила

- Свои боевые ID **не кликать**. Тестовые устройства добавляются в AdMob UI или через
  `RequestConfiguration.TestDeviceIds` (убрать код перед релизом). Новые тестовые
  устройства обычно начинают получать тестовые объявления за ~15 минут, иногда до 24 ч.
- Тестовое объявление помечено «Test Ad». Объявления через медиацию ярлык **не** получают.
- Редактор Unity показывает заглушки-prefab (с версии плагина 5.4.0) **под** вашим GUI;
  на устройстве реклама рисуется поверх. Раскладку проверять только на телефоне.
- Ad Inspector (в приложении) — для проверки загрузки, адаптеров, настроек приватности.

### 10.3 Сценарии

| Сценарий | Ожидание |
|---|---|
| Нет интернета | Слоты схлопываются, rewarded скрыт, игра работает |

| Rewarded закрыт до награды | GAMEOVER, кнопка исчезает, награды нет |

Автотесты (`HR.Core`, без Unity): правило «одно продолжение на забег», видимость
кнопки реворда, переходы `GameState` с `Countdown`, возврат к старой раскладке без MREC,
порядок сжатия раскладки (flex → зазоры 64→48 → старая раскладка) на сетке высот и комбинаций слотов,
без отрицательного flex-зазора и без зазора меньше 48.

| 5 | Заявка на production, листинг, Data safety, Ads declaration, app-ads.txt | 4 | проверка Play |
| 6 | Проверка app-ads.txt, мониторинг Policy center, невалидные клики, fill rate | 5 | 24 ч на crawl |
| 7 | Верификация личности, PIN, способ оплаты, первая выплата | доход $10 → $100 | недели–месяцы |

## 12. Критический путь

```
 Play-аккаунт ──▶ приложение в закрытом тесте ──▶ 14 дней ──▶ production
 AdMob-аккаунт ─▶ верификация ─▶ ad units ─▶ связь с Play ─▶ app-ads.txt
 Код (фазы 1–3) ──────────────────────────────┘
```

Самая долгая ожидаемая задержка — закрытый тест. Его можно начинать, как только есть
рабочая сборка, пусть и без боевой рекламы. Поэтому: **завести Play-аккаунт
первым**, и найти 12 тестеров заранее.
